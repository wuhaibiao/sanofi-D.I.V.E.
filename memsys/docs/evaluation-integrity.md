# 评测完整性规则

用户要求系统改进不能按评测题或标准答案定制，也不能根据答案改变提问和选题。后续开发按项目根目录的 `AGENTS.md` 执行。

通用字段保留、结构化存储和检索功能用自行编写的场景验证。不能查看预留集答案后补充提示词、语义规则或关键词，再用同一集合报告泛化效果。看过逐题反馈的集合保留为开发回归；新版本的一次正式验证需要预先固定未被开发触及的输入。

`scripts/evaluate_public_types.py` 的新运行使用三个冻结文件：

| 阶段 | 输入 | 隔离要求 |
|---|---|---|
| 写入 | `write-inputs.json` | 只有历史、日期和来源标识；没有评测问题、答案或证据标记 |
| 答题 | `read-inputs.json` | 固定原题、提问日期和来源标识；没有标准答案或历史正文 |
| 评分 | `judge-inputs.json` | 标准答案与独立评分信息；回答完成后使用 |

可信制样阶段按已经固定的题号和题型机械分离字段，不使用答案或已有表现来选择样本，不调用模型。运行时各阶段只读取对应文件，并核对字段白名单和哈希；缺少无答案文件时拒绝回退到旧的完整样本。输入构造器与生产代码、评测脚本一并冻结。回答与评分按运行和阶段隔离请求会话，禁止通过 provider 配置传入此前响应或会话链接。

2026-10-15 起，`run_relational_memory_eval.py` 与 `run_relational_memory_regression24.py` 的新运行按冻结选择顺序逐题执行，由 `question_serial_eval.py` 统一编排。每题在 `questions/0001` 等目录中保存各自的冻结输入、事实快照、实际提示、回答、错误和检索轨迹，并使用独立集合前缀与 namespace。顺序为：只写入当前题的全部历史会话 → 保存存储审计 → 回答一次 → 删除该题集合并验证为空 → 下一题。即使两题历史相同，也不复用上一题数据库。清理失败立即停止，不启动下一题；非评测集合不删除。所有题完成并清理后才由独立评分进程读取各自的标准答案，根目录 JSONL 为逐题原记录的汇总视图。

旧24题和32题记录采用的是全批写入后统一回答、按 corpus 隔离的方式，仍按原流程解释；不得改写旧结果为逐题清理评测。新编排只用自编场景和本地测试验证，不自动触发新的付费评测。

2026-10-25 用户授权约40题评测后，补查发现旧选题脚本只匹配部分样本与选择文件名，遗漏了旧版 hypotheses、trace 和写入日志。扩大为扫描 `runs` 下的 JSON/JSONL 题号元数据后，本地 LongMemEval Oracle 的500条样本、471个基础题号均有历史记录。因此本轮固定40题明确归为已暴露样本的开发回归；历史报告原件保留，其中“未使用样本”声明不再作为未暴露证据。新选择程序支持显式开发回归标记并记录实际重叠，不根据标准答案、内容、长度或旧得分选题。执行及结果目录为 `runs/memory-regression40-20261025`。

这些措施不能证明外部模型没有在预训练中见过公开数据，也不能使此前已看过的开发样本恢复成盲测。其他历史评测工具须先符合相同隔离边界，再用于新的验证；旧结果和冻结记录保留。

2026-10-14 排查没有发现已检查生产模块中的题目/答案硬编码或实际模型输入的额外答案注入。与此同时，开发确实查看过旧回归题及参考答案，因此不能保证过往满足上述严格开发边界。报告生成脚本中一处答案文字常量已移至结果数据。详细证据、限制和加固检查见 [审计报告](../runs/evaluation-integrity-20261014/report.md)。
