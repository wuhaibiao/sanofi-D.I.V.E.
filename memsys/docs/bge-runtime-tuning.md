# BGE 本地推理参数

`scripts/serve_bge_runtime.py` 复用已安装的 `memsys.embedding_server`，通过
`--threads` 和 `--batch-size` 设置计算线程及内部推理批量。默认仍为 4 和 2；
本聊天用户于 2026-11-04 授权将当前服务改为 8 和 8。

```sh
python scripts/serve_bge_runtime.py \
  --state-dir "$HOME/Library/Application Support/memsys" \
  --threads 8 --batch-size 8
```

启动器保持原 BGE-M3 权重版本、CPU FP32、输入顺序、1024 维单位向量和原有
HTTP 校验与鉴权。它预加载权重，健康接口报告实际线程数、内部批量、权重版本及
后端/启动器哈希。SIGTERM/SIGINT 停止监听后等待已接收请求完成。

这是部署层的参数修订。批处理和并行度可能引入浮点舍入差异，不能声称逐位一致；
自编短文本对照也不能证明完整评测的加速幅度或排名完全等价。

当前 500 题运行的变更记录在运行目录 `runtime-tuning.json`。切换时只暂停调度器，
让已启动的阶段进程自然结束，确认旧服务无活动连接后替换向量服务，再恢复同一个
调度器进程。已经产生的回答、失败、事实向量及审计记录不重做。

原 `freeze.json`、产品源码、评测工具和输入哈希保持原值；部署启动器单独记录哈希。
`runtime-tuning-backup/` 保留原启动项以及切换前的执行状态。记录包含切换时间、
切换时各题已经完成的阶段和受保护历史文件哈希。报告应标注先 4 线程/批量 2、
后 8 线程/批量 8 的混合基础设施配置，不能将最初冻结配置冒充为整轮实际配置。

此修订只调整向量服务。题目 worker 数、读取并发、重排模型、生成模型和提示词
均沿用原评测设置。

## 请求队列修复

用户随后授权暂停排查、修复后继续。修复后的启动器将所有模型推理交给一个常驻
执行线程。HTTP 连接线程只负责校验、提交和等待，避免每个连接轮流创建独立的
OpenMP 推理上下文。保持 8 个算子内计算线程及内部批量 8。

唯一任务数量由 `--max-pending` 限制，默认 16。同一输入的在途请求合并；完成后
短暂保留 30 秒的向量结果供网络重试读取，最多 32 份，仅存向量和输入摘要，
不保存原文、对话状态、问题答案或跨题推理上下文。已断开的排队请求在没有其他
等待者时取消；已经执行的计算完成一次后供重试读取。短查询可以先于批量写入，
但最多连续两次，避免写入饥饿。

健康接口增加执行线程、活动/排队任务和合并/重放/取消等计数。执行日志只记录
输入摘要、数量、字符数、排队时间、计算时间和 CPU 时间，不记录请求原文或凭据。
故障期间与修复后的基础设施边界另记于 `service-repair.json`，原
`runtime-tuning.json` 及其封印不改写。

维修使用预热替换：新服务先加载原权重，等待旧监听端口释放后接管。旧的题目阶段
不重新启动，正在等待的客户端仍遵守原有传输重试预算；旧的失败和重试不会重置。
新服务由登录启动项 `com.memsys.embedding.repaired` 管理，部署入口为应用状态目录的
`bge-runtime-repaired.py`。旧启动项归档，避免重启电脑后旧实现重新占用端口。

线程上下文问题的背景参见
[PyTorch 2.2.2 的 CPU 线程说明](https://github.com/pytorch/pytorch/blob/v2.2.2/docs/source/notes/cpu_threading_torchscript_inference.rst)。
