## 第一阶段 约束接口故障与执行耗时

保留v69已经完成的故障传播修复，先补足整题的执行预算。读取步骤共用网络重试预算，避免底层客户端和外围包装器各自重试。下一候选拟采用每次远端调用最多一次额外网络重试、整题额外网络重试最多两次、整题墙钟预算180秒；请求超时须随剩余预算收紧。格式修正与语义修正仍分别记录，也受整题总预算约束。

必需的来源读取、计算修复或来源复核遭遇接口故障时，返回明确的服务错误并保留未完成状态。正常的来源不足拒答、计算无效和已完成回答保持各自状态。非必需步骤的降级须单列原因。评分的网络错误与回答错误分别记录；已完成的Boolean标签始终保留。

云端冒烟验证最多10分钟，连续两次同类接口故障就停止该轮；不在同一轮不断续跑。新预算属于后续候选，暂停的冻结候选及历史记录保持原样。

交付：读取预算与错误状态的代码、可取消的超时处理、真实历史错误的本地回放、运行与停止命令。

验收：故障不会变成记忆不足；所有网络尝试、等待及失败耗时可核对；正常拒答不被重采样；停止后没有继续执行的评测请求。相关位置为`read_retry.py`、读取模型客户端、`core.py`、两类分页读取器、`aggregation.py`及评测执行器。写入链路的重试策略单独管理。

## 第二阶段 减少重复读取与复核

先统计每题各阶段的调用数、输入量和等待时间，找出已经读取或校验过的证据再次进入模型的路径。仅在本次请求内复用已验证证据；缓存须绑定源码、提示词、模型配置和记忆版本。

优先建立范围明确的直接查询及数量日期短路径。只有来源、角色、事件状态、时间范围和单位可以完整校验时，才允许一次证据抽取后用程序计算、去重及格式化答案。存在歧义、跨页遗漏风险、自然语言建议或状态冲突时，保留必要的语义复核。先在历史轨迹上验证适用范围，再增加真实模型调用。

交付：一次请求的证据复用、短路径适用条件与回退条件、按题型统计的调用和耗时报告。

首轮性能目标为单题中位耗时不超过90秒、第95百分位不超过180秒；这是待验证目标。报告同时列出全部请求耗时、成功回答耗时、覆盖率和服务失败数，避免靠更早失败造成表面提速。只有已正确案例无新增回退、完整正确率不下降时才采用。

## 第三阶段 固化跨会话和时间推理的已有收益

每次只处理一类有真实失败证据的问题。复用已有证据和计算结构，先统一字段及状态判断，避免继续增加相互干扰的全局提示规则。

| 能力 | 优化重点 | 必须保护的已验证行为 |
| --- | --- | --- |
| 跨会话汇总 | 区分累计快照与新增事件；统一数量、单位和来源；按事件去重；核对计划与实际完成 | 两组鱼数17、午餐8份、徒步8英里、实际出席3个日期 |
| 信息更新与偏好 | 分别维护各对象的拥有状态和事件状态；完成报告优先；早期计划只作为有来源关联的补充 | 已有充电宝的建议、吉他完成地点、当前藏品数量 |
| 时间推理 | 保留原话中的相对时间及来源锚点；核对年份、完整周与余数；保留近似精度 | 跨年活动3天、时长3.5周、阅读21天及允许的包含端点差异 |
| 来源缺失 | 区分发生日期与会话记录日；对缺失端点保持不确定；保留评分疑点 | 无来源居住题的正常拒答；实际取消或测试日期缺失时不编造日期 |

相关模块为`queryops.py`、`aggregation.py`、`daycount.py`、`user_context.py`及读取路由。已有日期合计和拥有状态修复先作为回归保护；只有本地回放或真实调用证明仍有缺陷，才新增逻辑。

## 第四阶段 按层次评估

1. 建立12个代表案例的开发回归集，优先使用已有真实响应、引用和错误记录。覆盖上表的已正确案例，并加入来源不足与接口故障案例。本地检查验证证据、计算、状态及错误处理，不能替代模型正确率。
2. 本地回归与必要构建检查通过后，选择3至5个真正受本次修改影响的案例做云端验证，遵守10分钟和连续故障停止条件。正常完成的错误回答仍算错；不反复生成直到答对。
3. 有实测修复收益且已正确案例无新增回退后，才启动固定第一组24题回归。至少23/24，24条回答与原始Boolean评分完整，缓存和BGE覆盖完整，数字标签冲突为零。评分冲突单列，不手工改写标签。
4. 第一组通过后，才运行同一候选的第二组固定24题；也须至少23/24。两组共用同一源码、模型、配置、记忆库来源及并发条件。默认从1并发开始，和历史2并发的差异单列，不能把整组变化全部归因于代码。
5. 两组开发回归都通过后，再进行一次未参与调试的24题验收。按用户最新要求预先固定题号及配额：跨会话、信息更新、时间推理、用户事实、助手事实、偏好各4题。选择前核查采样、已有回答、评分和调试记录；题号和参考答案不得进入产品逻辑。先冻结选择，再运行，至少23/24。

先前仅检查74份采样清单时有261题未出现。继续核查采样、选择、答案、失败、耗时、审计、轨迹和诊断脚本后，全部500题均已出现在历史执行或调试记录中，原题库已没有满足“未参与调试”的新题。特别是更早的 `oracle-v2` 已有313题答案和184题错误记录，不能因它们未进入近期采样清单就当作新题。最后一组需采用未用过的公开数据集或新的真实会话，另行冻结适配、配额和评分方法；若继续使用原题库，必须标为开发回归。新题须按冻结写入配置实际写入并单独核算耗时；复用旧库的读取成绩不能代替新的端到端验收。

每个24题批次的读取执行预算为60分钟；到时保存断点、覆盖率和失败原因，不报告未完成的完整正确率。停止后先分析原因；确有服务恢复证据时，最多安排一次只补未完成题或缺失评分的恢复，已完成回答与标签保持原样。仍未完成就结束该候选的验收。健康的接口验证、原始评分和完整覆盖均通过后才能进入下一层。

用户已授权 Step 不可用时采用 GPT-6 Luna 等可用模型。正式候选固定使用经实际探测可用的模型，不在同一批次混用模型；模型变化单列，不能把结果差异全部归因于代码。95%目标仍以两组固定24题和一组新24题分别至少23/24、完整写入/回答/评分/来源覆盖为准。达到后继续处理有来源的剩余错误，争取100%；缺失来源及评分疑点单列，不能补造事实或修改原标签。
