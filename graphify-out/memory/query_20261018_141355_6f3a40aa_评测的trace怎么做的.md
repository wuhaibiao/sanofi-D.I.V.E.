# Q: 评测的trace怎么做的

## Answer

图谱检索扩展词：[trace, runner, usage, ledger, provenance, request, recall]。以当前 scripts/evaluate_public_types.py、question_serial_eval.py、src/memsys/core.py、llm.py、bench/provenance.py 及已存在V7 32题产物字段核对。评测trace是代码主动埋点的JSON/JSONL文件记录，不是已接入的分布式span追踪。
关联：输出目录/冻结prefix标识运行，purpose与write/read/judge区分阶段；answer/grade/recall用question_id，写入用corpus_id+session_id，通过冻结selection元数据关联题目和corpus。F事实ID、E原文轮次ID串联证据来源。当前逐题编排有questions/0001等各自冻结输入、隔离集合、execution记录，并在全部题回答清理后评分；旧V7 32题仍为批量写入后回答，不能回写成逐题清理。
埋点：CapturedChat.chat在调用前追加purpose/messages/tags到阶段prompts.jsonl，并用prefix+phase隔离会话scope。它只保存messages，不完整捕获HTTP请求体参数或所有原始响应。UsageLedger通过模型客户端在得到可记账返回后记录started_at、model、purpose、prompt/completion/cached tokens、总latency、retries、usage_reported、cost_known和tags，线程锁后追加JSONL。失败在相应阶段结果和执行日志留存，不能说所有失败尝试都有usage行。
写入日志包含原文一致性、保存和处理消息数、整理状态、WriteReport、耗时、错误、事实快照和计数。core._retrieve保存plan、最终排序前30候选摘要、重排细节、关系路径、selected、omitted、最终memory、预算单位、coverage、sources、存储revision。core.recall调用_save_trace按question_id文件名保存traces/<qid>.json。候选列表非完整dense/sparse原始命中，且默认在成功召回后才写trace；早期失败可能只有prompts/error而无trace。
答案文件保存memory_items、input_units、hypothesis、finish_reason、模型名、status、error和总elapsed；grade文件保存判分结果与attempts，标准答案仅评分阶段读取。源码/配置/阶段输入与工具哈希在setup检查，防止条件静默变化。已检查runs/relational-memory-v7-32-20261014有32份trace，字段与上述一致，未读取题目或参考答案正文。抽取结果保存解析后的facts，不等于保存所有抽取原始响应。
排障沿原始消息→写入完整性和事实快照→检索/关系/重排→selected/omitted/最终prompt→答案/判分检查。预算单位当前UTF8不能误作精确tokens；服务未报告usage和未配置价格须保留unknown。可以简历表述为按题号关联的结构化评测日志，覆盖抽取结果、检索候选、重排、预算、模型输入和调用开销，用于追踪错误发生阶段。
