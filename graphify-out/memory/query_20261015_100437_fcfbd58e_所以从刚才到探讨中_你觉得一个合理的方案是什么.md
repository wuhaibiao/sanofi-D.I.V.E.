# Q: 所以从刚才到探讨中，你觉得一个合理的方案是什么

## Answer

Expanded from original query via vocab: [runner, reranking, namespace, session]. Proposed plan only, based on current serial controller and existing BGE HTTP wrapper. No production/configuration edits or evaluation/model calls this turn.
我建议采用：**服务常驻，逐题写入和回答，在线记忆按题清理，评测记录单独留档。**

| 对象 | 处理方式 |
|---|---|
| BGE权重、分词器 | 独立服务常驻，启动时加载并预热，模型参数固定 |
| 问题、候选、分词缓存 | 限制在单次重排请求内，正常结束或异常时都清理 |
| Qdrant服务 | 整轮保持运行 |
| 本题原文、事实、关系和向量 | 使用本题独立集合，回答后删除并核验 |
| 历史输入、事实快照、回答、判分 | 保存到结果文件，方便审阅，不再进入后续题的记忆库 |

每题执行：

**写入该题全部历史 → 检索该题事实 → 常驻BGE重排 → 独立请求回答一次 → 保存记录 → 清理本题集合 → 下一题。**

全部回答完成后集中评分，标准答案只在评分阶段读取。回答与裁判保持独立请求；评分模型按手册要求配置。

我仍建议评测时清理在线旧题记忆：它们不参与后续题，离线留档已经能满足复查需求。这样更容易核对题间隔离，也不会不断积累评测数据。

**当前逐题清库已经实现；接下来需要完成BGE常驻接入和请求缓存自动清理。** 先用自编场景检查“A题→B题→A题”的结果一致性及异常清理，再分别记录模型加载、重排和建删库耗时。这些检查不需要重新跑32题。
