# Q: 接入agent后怎么工作的

## Answer

Expanded against existing graph vocabulary: [agent, hook, recall, session]; old graph used only for navigation, current implementation verified from client.py, hook.py, mcp.py, agent_adapter.py and local-deployment.md. Agent remains responsible for planning, tool use and final generation. Typical host orchestration: bind stable user and external session identity; persist user/assistant turns via add_turn; before generation call recall(query,budget,coverage_budget), place returned context/rules with the host prompt and short-term working window; host invokes its answering model and persists final assistant response. End_session or host-managed flush schedules/conducts consolidation: full batch plus related old facts, extraction model, validation/dedup/new facts, embeddings/entity-relation indexes to Qdrant. Raw turns persist immediately, but facts-only cross-session recall sees new information after consolidation publishes successfully. Default recall uses embedding/lexical retrieval and BGE reranking rather than generative query planning. HTTP client exposes operations but does not auto-orchestrate every agent turn; hooks implement user-submit recording/recall injection, Stop recording and SessionEnd consolidation; MCP tools alone rely on explicit tool calls and do not guarantee automatic recording or recall. Memory API does not observe or judge arbitrary external-Agent answers. Same authorized user/storage scope can share long-term facts across sessions; recent working window remains host-managed.
