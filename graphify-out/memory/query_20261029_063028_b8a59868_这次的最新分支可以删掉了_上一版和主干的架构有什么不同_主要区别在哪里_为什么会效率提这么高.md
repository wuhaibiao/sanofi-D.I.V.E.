# Q: 这次的最新分支可以删掉了，上一版和主干的架构有什么不同，主要区别在哪里，为什么会效率提这么高

## Answer

Expanded from original query via graph vocab: [selection, rerank, extract, structure, usage, seconds]. Existing graph located Selection, Writer._extract, Retriever.rerank and UsageLedger; graph predates the experiment, so live Git diffs and frozen evaluation summaries were checked. The failed latest local branch codex/memory-top20-refinement at 6b1216c was deleted after preserving its patch and keeping the previous version 67b1348 as codex/memory-top20-previous in the same clean worktree. All 300 main snapshot files and main HEAD/status/index were unchanged, as were 1423 files in the two original evaluation directories. Previous versus main keeps the same fact store, candidate retrieval, BGE backend, source priority, temporal handling and single answer call. Changes add metadata and compact-source rules in the same extraction request, compact adjacent literal fields and wholly covered structures, round-robin explicit identities within source priority, and uniformly cap final selected facts at 20 rather than ordinary 30 / broad 60 / supplementary 128. Candidate retrieval is not capped at 20 and raw BGE rank is not the final selection order. Generative production calls remain 53 = 33 extraction + 20 answer; judge 20 is separate and both variants used zero extra selector calls. Prompt facts average 37.95 to 15.85 and answer input tokens 186117 to 90442 (-51.4%); overall input/output tokens fall 16.7%/15.9%, while extraction input rises 9.6%. Read plus answer mean falls 50.24 to 19.37 seconds, but observed provider answer-request mean falls 36.44 to 4.06 seconds while BGE mean increases 11.76 to 13.60 seconds with 716 windows in both runs. Transport retries were 6 versus 0 overall, including 2 versus 0 in answering. This locates most observed speedup in remote request time but does not isolate context size, upstream processing or transport as causal components. Historical runs are not contemporaneous A/B measurements. Original scores remain 19/20 versus 18/20; efficiency improvement is not proof of quality preservation. Main and runtime were not changed, no new evaluation was run.
