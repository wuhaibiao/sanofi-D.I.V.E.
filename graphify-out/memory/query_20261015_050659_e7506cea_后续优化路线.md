# Q: 后续优化路线

## Answer

Expanded from original query via vocab: [reranking, retriever, tokenizer, budget, memory].
建议下一轮先做**候选控制、按需重排和事实压缩**，保持现有模型、FP32 和 batch=4。

当前两道跨会话题中，模型推理及结果读取占重排耗时的 **99% 以上**；继续优化分词的收益已很有限。[实测记录](/Users/OleniusBlanc227/Documents/sanofi/memsys/runs/rerank-cross-session-two-20261014/report.md)

| 顺序 | 优化方向 | 具体措施 |
|---|---|---|
| 1 | 减少重排工作量 | 普通查找先按实体、属性和时间缩小范围，尝试20–30条重排预算，并计入长事实产生的多个窗口。跨会话汇总保留全部贡献项、关系和版本链，不能统一截断Top-K。 |
| 2 | 按需调用BGE | 仅当筛出的相关事实全部能放入预算、版本链已处理，而且最终输入不受排序影响时跳过重排；其他情况继续使用BGE。 |
| 3 | 减少回答输入 | 在现有去重基础上，减少句子、value、relations之间的重复表达，降低无关助手建议占比。完整事实留库，实体、数值、单位、关系、时间和限定条件保留。 |
| 4 | 完善更新与数量语义 | 同一实体、属性和统计口径才比较版本；区分累计值、单次增量、计划与已发生事件。有效性由有效时间和明确更新关系决定，不能一律按记录时间覆盖。 |
| 5 | 优化推理后端 | 前面完成后，再验证同一BGE的ONNX Runtime＋CoreML部署，随后考虑小模型或FP16。 |

CoreML可调用Apple的CPU、GPU和Neural Engine，但BGE的算子覆盖、输入形状和本机性能仍需验证，不能预设一定更快。[官方文档](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)

**第一轮建议只实施前3项。** Batch=8此前没有稳定提速，FP16出现过Top-5变化，暂不直接切换。

验收应记录完整在线链路的P50/P95、实际输入tokens和证据覆盖。开发用自编通用场景；旧24题只作回归，泛化效果需用事先冻结的未使用题检验。
