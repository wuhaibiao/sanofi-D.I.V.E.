# Q: 所以是不是可以保留最近的十几条对话然后其他的全都抽取成事实，存入库，用的时候把工作经验和长期记忆结合起来回答，但是这种设计没有实体关系，是否考虑用知识图谱或者图数据库呢，分析一下

## Answer

建议采用近期工作记忆、长期事实和实体关系索引。当前 Fact 已有 subject/attribute/value 和时间字段，能表达弱三元组；但缺少统一实体 ID、别名消歧、明确的关系对象和图遍历。WebChat 的 chat_window_turns=12 实际裁剪 12 条消息，约六轮；建议按完整轮加上下文预算控制，并在淘汰前检查 Writer 写入成功，失败保持待处理状态。旧对话不能保证单次无损抽取；只存档的原文不会弥补本次回答的遗漏。关系层应作为事实的关联索引，指向同一事实 ID，召回去重，避免重复占据候选与上下文。新增实体 ID、关系类型、目标实体、业务状态、有效期、记录时间、来源及限定条件，重复事件采用独立事件 ID，谨慎处理同名与别名。LLM 提取候选，程序校验字段、来源、去重和受控合并。推荐先在现有 Store/Qdrant 记录上增加关系字段，由程序做有范围和预算的一到两跳扩展，而不是立即迁移数据库。知识图谱是数据模型，Neo4j 是可选存储与遍历引擎；复杂、多跳、频繁路径查询和关系规模上升后再考虑专门图数据库。Graphiti 是时态知识图谱构建框架，保留实体、关系时间和来源 episode，可参考但不是数据库本身。回答先做语义检索和实体定位，再扩展相关关系，时间过滤、事实 ID 去重、覆盖检查及必要补取，最后将有限事实与近期对话一起交给 LLM 一次作答。工作经验若指方法与教训，应另存适用条件、步骤和验证结果，不能把助手建议直接当成用户事实。收益主要是跨会话实体关联、关系完整性及时间状态查询；增加抽取和索引维护成本，实体误合并会放大错误，图存储不能恢复根本没有抽取出的关系。验证只采用事先自写的通用多跳、别名、状态变更与重复事件场景，不查看评测标准答案来设计规则。查询扩展词：Fact Writer WebChat Store；开发图谱是旧索引，结论以当前 schema.py、webchat.py、write.py 代码和当前配置为准。
