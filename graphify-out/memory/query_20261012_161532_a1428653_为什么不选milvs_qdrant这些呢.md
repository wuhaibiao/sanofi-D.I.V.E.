# Q: 为什么不选milvs,qdrant这些呢

## Answer

Expanded via graph vocab: [store, vector, retrieval, index, state, version, source, transaction]. Interpret milvs as Milvus. Qdrant and Milvus should be considered; previous small per-question/Oracle-size rationale cannot exclude purpose-built vector engines for a real multi-user service. Distinguish authoritative memory storage (raw sources, facts, lineage, status changes and application transactions) from a pluggable retrieval index. Current SQLite can stay unchanged while a future Qdrant/Milvus index replaces in-process vector scanning and optionally lexical/hybrid recall, but this is only a proposed architecture, not an installation or change. Verified official Qdrant capabilities include indexed payload filtering, filterable HNSW, dense/sparse query fusion with RRF, tenant payload indexing and tiered tenant shards; single-node Docker quickstart provides a straightforward starting deployment. Verified official Milvus capabilities include scalar filtering and multiple multi-tenant strategies, built-in BM25 full-text/sparse retrieval, Lite/Standalone/Distributed deployment families, and disaggregated compute/storage in distributed architecture. Do not portray either as storing only vectors or Milvus as always requiring a large cluster. PostgreSQL plus pgvector remains a single-store candidate for relational sources and vector search. A two-store approach adds synchronization, retries/idempotence, stale version and forget/delete propagation handling; recommend authoritative-store outbox updates, replayable index sync, and source/status/version validation after retrieving candidates. Vector engines do not automatically replace entity resolution, state update reasoning, provenance semantics, reranking or host answer generation, nor do they remove SQLite write locks/application locks. A provisional preference for considering Qdrant first for this filtered-memory retrieval service is an engineering judgment about feature fit and simple starting deployment, not evidence of lower latency than Milvus/pgvector. Milvus is a strong candidate when its index/deployment/distributed design fits operations requirements; workload scale remains unspecified. User says keep SQLite for now and prohibits evaluations until explicitly authorized. No software installed, runtime/config/database changes, model probes, performance tests or evaluations performed.
