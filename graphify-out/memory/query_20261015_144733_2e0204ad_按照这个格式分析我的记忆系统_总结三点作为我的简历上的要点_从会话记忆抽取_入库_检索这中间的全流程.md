# Q: 按照这个格式分析我的记忆系统，总结三点作为我的简历上的要点，从会话记忆抽取，入库，检索这中间的全流程，每个涉及到的模块都有可能被面试官问：为什么这么设计，有什么效果，有比较其他方案吗

## Answer

图谱扩展词来自现有词表：[memory, extract, write, read, retrieval, search, evidence, rerank, session]。现有图谱作为导航，当前实现以 memsys/src/memsys 的源代码和既有冻结报告核验。
简历三条主线：1. 完整轮工作记忆、淘汰前整理、每个正常非空批次一次 LLM 同时抽取事实实体关系、结构值保真和来源关联。2. Qdrant 统一原文、事实、索引、关系和持久任务，消息幂等、处理水位、租约恢复、不可变版本和租户发布头条件更新控制多记录可见性。3. BGE-M3 dense + 稳定哈希词法 sparse、相似度加权排名融合、BGE cross-encoder、最多两跳关系扩展、事实ID去重、预算和覆盖说明；默认仅事实上下文。
当前源码核验：Writer.consolidate 在事务外完成抽取和embedding，事实版本和水位未变时重试短提交而复用模型结果。salience 只影响原文检索索引，不在有抽取模型时过滤整批抽取。抽取不按长度分块，超限或不完整输出整批失败；已存原文保留。检索旧事实至多10条，已处理同会话安全消息至多10条，仅提供指代上下文，不是新证据。程序回补仅明确助手列表与Markdown表格，不声称完整语义覆盖。去重核对完整身份，不自动覆盖旧事实；无发生标识的事件跨会话不凭相同文本合并。关系与实体是事实的索引，不作为独立向量证据；别名须显式来源，关系最多2跳、32节点、96边、32候选，主动遗忘不可充当桥梁。
当前部署白名单配置核验：facts模式，BGE MPS float32 batch4，dense30/sparse30/rerank60；完整轮上限12、窗口12000 UTF8字节；当前本机worker_count=1，不能据源码默认4宣称已验证高并发。预算模式utf8，字段名tokens不能当服务器精确tokens。Qdrant应用发布协议不是SQL事务，也不是端到端exactly-once。归档可兜底，主动遗忘阻止事实和来源旁路召回。
效果证据：V7构建记录170项适用功能检查与8项真实Qdrant检查，不是并发性能证明。自编固定64候选、6个唯一查询、每变体18个预热后MPS测量，采用fp32 batch4分词缓存后编码字符1865930→1194848（减少35.965%），总体中位2.885525→2.779172秒（降低3.686%），18次分数和Top5一致。FP16 Top5仅14/18一致未采用；batch8未达事先5%采用阈值。不能换算成端到端时延或准确率提升。
评测口径：Oracle32题28/32，后续完整性审计确认30题有既往回答记录，按暴露后的开发回归解释；原24题23/24同为开发回归，含1题写入失败计入分母。不能称盲测或总体95.83%准确率，不能据此宣称优于Mem0。新逐题入库、答题、清理、下一题与末尾独立评分编排不能回写到旧结果。没有启动新评测或修改产品。
备选方案核对官方来源：Mem0当前官方add是additive流程，不能泛称其必须执行UPDATE/DELETE。Letta侧重有状态Agent与可编辑核心记忆块；本系统提供独立记忆服务。Graphiti侧重时间图与关系检索，本系统采用Qdrant内有界事实关系索引，未证明完整图系统替代。pgvector提供Postgres事务和JOIN优势；Qdrant统一后端的代价是自建多记录发布协议，不能无实测宣称更快。
